- **2026-07-22**: Step 4 attempted, then fully reverted — recorded here so the next attempt doesn't re-walk the same dead end. Built image upload UI (`ImageUpload.tsx`, `CandidatePicker.tsx`), a `web_search_20260318` tool (newer than the plan's `20260209`, confirmed a drop-in replacement), and a `present_item_candidates` client-facing tool per the plan's Cross-cutting decisions. First real-screenshot test surfaced a serious bug: given an actual item icon, the model skipped every tool and answered directly from its own training-data recall of what the icon "looks like" — confidently, and wrong. The candidate-flow design in the plan assumed the model's *self-reported* uncertainty would naturally surface ambiguous cases; this proved that assumption false — a clean, unambiguous-looking icon still produced a confidently wrong single guess with no grounding at all. Tried hardening this two ways: (1) code-level `tool_choice` forcing so an image turn could only ever call `present_item_candidates`, never answer directly — fixed the "never asks" bug but did nothing for accuracy, since candidates were still pulled from the same untrustworthy memory recall; (2) a two-pass pipeline (`lib/imageIdentification.ts`): propose 3-5 name hypotheses → validate each against real OpenDota data (dropping hallucinated names, swapping in OpenDota's own verified icon URL) → re-show the original screenshot alongside the *real* reference icons and have the model visually re-confirm matches via a `confirm_item_matches` tool, only surfacing confirmed survivors. This was meant to replace blind recall with actual image-to-image comparison. Live-tested twice against a real, correctly-cropped Falcon Blade icon (fetched directly from OpenDota's own CDN, so the reference set necessarily contained the exact right answer) — both times the confirm-match step rejected all candidates, including the correct one, meaning the visual re-comparison step itself is unreliably strict, not just the original recall step. Given two failed approaches, the user asked to shelve the whole feature for now rather than keep iterating blind. **Everything reverted**: `app/api/chat/route.ts`, `lib/systemPrompt.ts` back to their Step 3.4 end-state; `lib/types.ts`, `components/ChatInput.tsx`, `components/ChatMessage.tsx`, `components/ChatWindow.tsx` back to pre-Step-4 versions; `lib/opendota.ts`'s Step 4 additions (`img` field, `resolveItemCandidate`) removed; all new files deleted (`components/ImageUpload.tsx`, `components/CandidatePicker.tsx`, `lib/tools/webSearchTool.ts`, `lib/tools/presentCandidatesTool.ts`, `lib/tools/proposeItemNamesTool.ts`, `lib/tools/confirmItemMatchesTool.ts`, `lib/imageIdentification.ts`, and the `.claude/skills/image-item-identification` skill doc). `docs/plan.md`'s Step 4 status reverted to `⬜` with no structural changes, so the plan's own Step 4.1/4.2 file lists still describe a reasonable starting point. **Worth knowing before the next attempt**: the core problem is unverified reliance on a vision model's from-memory icon recognition — neither "ask it nicely," "force a tool call," nor "make it double-check itself" fixed that, since all three still trusted the same model's own visual judgment at some point in the pipeline. A future attempt probably needs either a fundamentally non-LLM-vision approach (e.g. perceptual-hash/embedding similarity search against OpenDota's real icon catalog, done in code rather than asked of the model) or a much more constrained/simplified LLM-vision prompt (e.g. single side-by-side comparisons one at a time rather than a batch, or additional context/crop cues) — not verified as fixes, just untried directions.
